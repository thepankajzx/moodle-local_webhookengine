Core Architecture

1. Non-Blocking Async Queue Architecture

The Event Webhook Engine uses a decoupled, event-driven pipeline designed to eliminate latency for students and teachers. Student interactions (quiz submissions, course enrolments, grade calculations) trigger lightweight in-memory events that write to a local queue table (mdl_local_webhookengine_delivery) in under 2 milliseconds. Background Moodle ad-hoc tasks independently fetch, sign, and dispatch webhooks to remote endpoints with automatic retries.

1. Event Interception

Moodle core events are captured synchronously by the observer class, evaluating match filters without blocking the PHP user thread.

2. Async Task Queue

Payloads are pre-compiled, signed with HMAC-SHA256, and queued into Moodle's native ad-hoc task runner.

3. Resilient Dispatch

Parallel workers deliver requests with configurable timeouts, capturing HTTP status codes, response headers, and retry timestamps.

Configuration Deep Dive

3. Global Engine Settings

Access these parameters in Site administration → Plugins → Local plugins → Event Webhooks → Settings. Each setting controls system resilience, rate capping, and server resource conservation.

1. Global Enable Switch (`enabled`)

Default: Enabled

Acts as the master circuit breaker for the entire webhook pipeline. When disabled, all incoming Moodle event observers exit instantly with zero database operations, allowing emergency pausing during server maintenance or migration without losing existing hook configurations.

2. Request Timeout (`request_timeout`)

Default: 10 Seconds

Defines the maximum time in seconds Moodle will wait for your external endpoint (n8n, Zapier, Webhook receiver, or custom API) to acknowledge an HTTP POST request before declaring a connection timeout and scheduling a retry.

3. Max Retry Attempts (`max_retries`)

Default: 5 Attempts

Controls how many times the engine will re-dispatch a failed webhook (e.g., HTTP 500, 502, 503, or connection timeouts). Retries use an exponential backoff formula (2^(attempt) * 60s) to prevent overloading recovering target servers.

4. Delivery Log Pruning (`log_retention_days`)

Default: 30 Days

Moodle automatically deletes completed webhook delivery records older than this retention period via a scheduled background task (\local_webhookengine\task\purge_logs). Keeps your database lean even with millions of monthly LMS interactions.

5. Enforce HTTPS (`ssl_verify`)

Default: Strict HTTPS

Requires all destination endpoints to use encrypted https:// URLs with valid SSL certificates. Can be toggled OFF strictly in local development or staging environments to allow testing with http://localhost:5678 or internal IP subnets.

6. Max Delivery Rate Limit (`rate_limit`)

Default: 120 req/min

Enforces a sliding-window rate limit per endpoint. If a massive quiz attempt or bulk user upload triggers thousands of simultaneous events, the engine automatically buffers dispatches to prevent exhausting downstream API rate caps or triggering HTTP 429 Too Many Requests errors.

Webhook Configuration

4. Creating & Managing Webhooks

Create new webhook endpoints under Site administration → Plugins → Local plugins → Event Webhooks → Manage Webhooks.

Key Form Fields Explained:
  • Name: A descriptive internal label (e.g., "HubSpot CRM Sync", "n8n Quiz Auto-Grading").
  • Destination URL: The target HTTP/HTTPS POST endpoint URL.
  • Secret Token: A 32+ character key used to compute HMAC-SHA256 request signatures for bank-grade verification.
  • Subscribed Events: Select one or more Moodle core events to stream to this endpoint.
  • Custom HTTP Headers: Optional key-value pairs sent with every request (e.g. Authorization: Bearer token123, X-Custom-Env: production).
  • Course / Module Filter: Optional restrictor to ensure webhooks only fire for specific course IDs or activity module contexts.

Security & Authentication

6. Bank-Grade Security & HMAC-SHA256 Verification

Every HTTP POST request sent by the engine includes two cryptographic security headers: X-Moodle-Signature-256 and X-Moodle-Timestamp. This guarantees payload integrity and prevents replay attacks.

How Signature Verification Works:
  1. Moodle concatenates the UNIX timestamp and the raw JSON request body: payload_to_sign = timestamp + "." + raw_json_body
  2. Calculates the HMAC-SHA256 hex digest using your configured secret token.
  3. Your receiving server computes the same hash and verifies using constant-time comparison (hash_equals in PHP or crypto.timingSafeEqual in Node.js).
  4. Rejects any requests where |current_time - timestamp| > 300 seconds to prevent replay exploits.
Python Verification Example (FastAPI / Flask):
import hmac, hashlib, time

def verify_moodle_webhook(raw_body: bytes, timestamp: str, signature: str, secret: str) -> bool:
    # 1. Reject if timestamp is older than 5 minutes (Replay defense)
    if abs(time.time() - int(timestamp)) > 300:
        return False
    # 2. Recompute expected HMAC-SHA256 signature
    message = f"{timestamp}.".encode('utf-8') + raw_body
    expected = hmac.new(secret.encode('utf-8'), message, hashlib.sha256).hexdigest()
    # 3. Constant-time string comparison
    return hmac.compare_digest(expected, signature)

Solutions & Real-World FAQs

8. Troubleshooting & Common Administrator Questions

Step-by-step resolutions for the 12 most frequent server, cron, SSL, and network scenarios encountered by LMS administrators.

Q1 Webhook deliveries remain stuck in "Queued" status and never dispatch Cron Issue

Root Cause: Moodle's background ad-hoc task cron runner is not executing on your server.

Solution: Webhooks are processed asynchronously by background tasks. Test manual execution via server CLI:

php /path/to/moodle/admin/cli/adhoc_task.php --execute

Ensure your server crontab (Linux) or Windows Task Scheduler runs php admin/cli/cron.php every 1 minute.

Q2 Admin submitted a quiz attempt, but `attempt_submitted` event was not logged Moodle Core Logic

Root Cause: Moodle classifies Administrator and Teacher quiz submissions as Previews (preview = 1).

Solution: Moodle core suppresses \mod_quiz\event\attempt_submitted during previews and fires \mod_quiz\event\attempt_preview_started instead. Real attempt_submitted events are exclusively fired when an enrolled Student submits a quiz. Both events are supported.

Q3 Saving endpoint gives "Only secure HTTPS URLs are permitted" Security

Root Cause: Plain HTTP endpoints are blocked by default for production security.

Solution: For local development (e.g. testing with local Docker n8n on http://localhost:5678), go to Site admin → Plugins → Local plugins → Event Webhooks → Settings and disable Enforce HTTPS Only.

Q4 n8n or Zapier returns HTTP 401 / "Invalid Signature" error HMAC Signature

Root Cause: Automation tools sometimes parse and re-stringify the JSON body, changing whitespace and corrupting hash validation.

Solution: Ensure your webhook receiver validates the signature against the raw unmodified HTTP request body bytes before JSON parsing.

Q5 Deliveries show HTTP 504 or Connection Timeout during large exam spikes Performance

Root Cause: The destination API server cannot handle the influx of simultaneous webhook connections.

Solution: In plugin settings, configure the Rate Limit slider to 60 req/min and set Request Timeout to 15s. Moodle will buffer dispatches without failing student attempts.

Q6 How do I filter webhooks for a specific course or category only? Filtering

Solution: In the Webhook Edit form, populate the Course Filter field with target Course IDs (e.g. 5, 12, 48). Events generated in other courses will be silently ignored before queuing.

Q7 Does this plugin slow down student page loads or quiz submissions? Zero Latency

Answer: No. The engine uses 100% asynchronous background ad-hoc tasks. When a student submits an assignment or quiz, Moodle inserts a queue record in under 2ms and finishes the page render immediately without waiting for HTTP connections.

Q8 How can I replay a failed webhook delivery without re-triggering user actions? Deliveries

Solution: Navigate to Site admin → Plugins → Local plugins → Event Webhooks → Delivery Logs. Locate the failed delivery row and click the Replay button. The payload will be re-queued and dispatched immediately.

Q9 What happens if the receiving endpoint goes down for several hours? Resilience

Answer: Deliveries transition into Retry status. The engine retries up to your configured Max Retries (default 5) with exponential backoff. Once the target endpoint recovers, queued deliveries succeed automatically.

Q10 How do I transfer my Pro License when migrating to a new domain? Licensing

Solution: Email support@thedefinite.one with your purchase invoice number and your new Moodle domain URL. A new offline key will be issued immediately with zero downtime.

Q11 How is database table bloat prevented over time? Maintenance

Answer: The engine includes an automated scheduled task (\local_webhookengine\task\purge_logs) running daily to delete successful delivery logs exceeding your retention threshold (default 30 days).

Q12 How to test webhooks on a local development setup? Local Dev

Solution: Use tools like Docker n8n (http://localhost:5678/webhook/...) or ngrok tunnels. Remember to set Enforce HTTPS Only to No in plugin settings when testing HTTP local URLs.
